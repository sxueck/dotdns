# dotdns 统计可读化、持久化与证书校验日志

## Goal
- 将 `dotdns status` 输出的 uptime 从原始秒数改为人类可读格式（如 `14h 14m 27s`）
- 统计计数器在服务重启后保持不变（持久化到文件）
- 服务启动时在日志中输出 TLS 证书校验结果（subject, issuer, 有效期）

## Scope
- In scope: `MetricsSnapshot::to_human_string()` 的 uptime 格式化
- In scope: 累计计数器持久化到 `/var/lib/dotdns/stats.json`（可通过配置修改路径）
- In scope: SIGINT/SIGTERM 优雅关闭时的 stats 保存 + 每 60 秒定期保存
- In scope: TLS 证书详情日志（subject, issuer, not_before, not_after）
- In scope: `format_uptime()` 单元测试、持久化读写测试、恢复计数器测试
- In scope: 示例配置或文档中说明 `stats_path` 的默认值和用途

## Non-Goals
- 不持久化 DNS 缓存条目
- 不恢复 `cache_entries`，该字段是当前内存缓存大小 gauge，重启后应反映新进程的缓存状态
- 不持久化挂起的查询去重映射表
- 不持久化封禁列表规则（已通过 download_dir 支持）
- 不把管理 API 输出结构 `MetricsSnapshot` 直接作为磁盘持久化契约
- 不做证书过期预警或自动续期

## Constraints
- 保持与现有 `tracing` 日志框架一致
- 持久化文件使用原子写入（临时文件 + rename）防止写崩溃损坏
- `start_time` 仍使用 `Instant`（每会话独立），计数器累加
- TLS 证书日志只能附加在现有 rustls config 构建成功路径之后，不能弱化证书/私钥匹配校验
- stats 文件写入不在 DNS 请求热路径中执行；定期/关闭保存可使用低频同步写入或 `spawn_blocking`
- 遵循项目现有代码风格：`thiserror` 错误类型、`Arc` 共享、`tokio::spawn` 后台任务

## Context Facts
- `MetricsRecorder` 位于 `src/metrics.rs:7-15`，所有计数器为 `AtomicU64`，`start_time` 为 `Instant`
- `MetricsSnapshot` 已派生 `Serialize`/`Deserialize`（`src/metrics.rs:73`）
- `to_human_string()` 位于 `src/metrics.rs:84-103`，当前输出 `uptime: {}s`
- 服务启动编排在 `src/main.rs:143-220` 的 `run_serve()` 中
- `validate_tls_config()` 位于 `src/server.rs:175-177`，成功后静默返回
- `build_tls_server_config()` 位于 `src/server.rs:179-204`，解析证书和私钥
- 项目已依赖 `rustls`、`rustls-pemfile`，用于 TLS 处理
- blocklist 默认下载目录为 `/var/lib/dotdns/blocklists`（`src/config.rs:358`），systemd 已配置 `StateDirectory=dotdns`
- 当前优雅关闭只通过 `tokio::signal::ctrl_c()` 处理 SIGINT（`src/main.rs:217`），systemd 停止/重启常用 SIGTERM，需要新增 Unix signal 处理

## Evidence & Assumption Audit
- Assumption: `x509-parser` v0.16 可以解析 rustls 的 `CertificateDer<'static>`（即 `Der<'static>`）
  Evidence: `Der<'static>` 实现 `AsRef<[u8]>`，`x509-parser::parse_x509_certificate` 接受 `&[u8]`
  Consequence if wrong: 需要使用 `x509-parser` 的不同版本或改用 `der-parser` 手动解析
  Status: resolved
- Assumption: `/var/lib/dotdns/` 目录在 systemd 环境下由 `StateDirectory=dotdns` 保证存在且可写
  Evidence: systemd service 文件 `packaging/systemd/dotdns.service:25-29` 已声明
  Consequence if wrong: 非 systemd 环境下需手动创建目录，`save_stats` 已含 `create_dir_all`
  Status: resolved
- Assumption: `cache_entries` 不应跨重启恢复
  Evidence: `Cache::new()` 在 `src/cache.rs:65` 初始化时调用 `metrics.set_cache_entries(0)`，且 spec 明确不持久化 DNS 缓存条目
  Consequence if wrong: status 会显示不存在的缓存条目数量，造成运行状态误导
  Status: resolved
- Assumption: TLS 校验日志不能替代现有 rustls 校验
  Evidence: `build_tls_server_config()` 在 `src/server.rs:200-203` 使用 `with_single_cert(certs, key)` 构建配置，该路径会校验证书链和私钥是否匹配
  Consequence if wrong: 可能把 cert/key mismatch 从启动失败变成启动成功，造成安全回归
  Status: resolved

## User Outcomes
- `dotdns status` 输出 `uptime: 14h 14m 27s` 而非 `uptime: 51267s`
- 服务重启后，累计查询数、缓存命中、缓存未命中、封禁数、上游失败数继续累加而非归零
- 服务重启后，`cache_entries` 反映当前进程内存缓存条目数，不从磁盘恢复历史值
- 启动日志中可看到类似 `TLS certificate verified successfully subject=CN=example.com issuer=CN=CA not_before=... not_after=...`

## Functional Requirements
- FR-1: `to_human_string()` MUST 输出可读 uptime 格式（d/h/m/s 组合），< 60s 时仅显示秒
- FR-2: 服务启动时 MUST 尝试从 `stats_path` 加载内部磁盘结构 `PersistedMetrics`，成功则初始化累计计数器
- FR-3: 服务优雅关闭（SIGINT 和 Unix SIGTERM）时 MUST 将当前累计计数器写入 `stats_path`
- FR-4: 服务运行时 MUST 每 60 秒自动保存一次累计计数器到 `stats_path`
- FR-5: 持久化写入 MUST 使用原子操作（先写临时文件，再 rename）
- FR-6: 加载持久化文件失败（损坏、不存在）时 MUST 静默降级为从零开始，不阻塞启动
- FR-7: TLS 证书验证通过后 MUST 使用 `tracing::info!` 记录证书的 subject、issuer、not_before、not_after
- FR-8: 证书解析失败时 MUST 使用 `tracing::warn!` 记录警告，不影响服务启动
- FR-9: TLS 证书日志 MUST 保留现有 `build_tls_server_config()` / `with_single_cert` 校验语义，不得以单纯读取 cert/key 文件替代 rustls 配置构建
- FR-10: `cache_entries` MUST NOT 从持久化文件恢复；它应由 `Cache::new()` 和缓存变更逻辑继续维护当前进程状态

## Non-Functional Requirements
- NFR-1: 持久化文件大小 < 1KB（JSON 格式，仅累计计数器字段）
- NFR-2: 持久化写入不在 DNS 请求热路径中发生；若实现使用同步文件 I/O，应仅在后台任务或关闭路径执行
- NFR-3: 新增依赖 `x509-parser` 应为纯 Rust crate，无需系统库

## Edge Cases
- Scenario: stats 文件被手动修改为无效 JSON → Expected: `tracing::warn!`，删除损坏文件，从零开始
- Scenario: stats 文件所在目录不存在 → Expected: `save_stats` 调用 `create_dir_all` 自动创建
- Scenario: 磁盘满导致写入失败 → Expected: `tracing::warn!`，静默跳过本次保存，不崩溃
- Scenario: systemd stop/restart 发送 SIGTERM → Expected: 进入优雅关闭路径并保存 stats
- Scenario: 进程被 SIGKILL 或崩溃终止 → Expected: 最多丢失最近一次 60 秒周期保存后的增量
- Scenario: 服务重启但 DNS 缓存未持久化 → Expected: `cache_entries` 从 0 开始并随新缓存写入变化
- Scenario: 证书链为空（certs.is_empty()） → Expected: 已有错误处理 `return Err(...)`，不进入日志函数
- Scenario: 证书 DER 解析失败（非标准证书） → Expected: `tracing::warn!`，服务继续运行

## Shared Contracts
- Contract: `PersistedMetrics` 的 serde JSON 格式是磁盘持久化契约
  Owner: `src/metrics.rs`
  Consumers: `src/main.rs`（加载/保存）
  Notes: 只包含累计计数器，不包含 `uptime_secs` 或 `cache_entries`；字段增减需考虑向后兼容（新增字段用 serde default）
- Contract: `MetricsSnapshot` 仍是管理 API/status 输出契约
  Owner: `src/metrics.rs`
  Consumers: `src/management.rs`, CLI status 输出
  Notes: 不直接作为磁盘文件格式，避免 API 输出变化影响持久化兼容性
